# Revue et preuve CI des schemas, 27 septembre 2026

## Etat de la revue

Revue en lecture seule du code, suivie de controles dans l'image exacte
`alpine/k8s:1.35.4` sur le moteur dedie D. Aucun code de production ou de test
n'a ete modifie par ce lot ; seul ce rapport est ecrit dans le depot.

Deux faux verts ont ete reproduits en memoire, signales puis corriges par le
proprietaire avant la copie source :

- Un plan sans HelmRelease retournait le succes avec zero chart valide.
  Il est maintenant refuse avant le telechargement des schemas.
- Le garde Velero dependait du nom de release `velero`. Son dispatch utilise
  maintenant l'identite du chart ; le Deployment est identifie par son
  conteneur `velero`, y compris sous un autre nom de release.

**Historique du premier controle reel : finding ouvert sur les unions CRD.**
Dans `scripts/verify-gitops.py`, `prepare_crd_schema` strictifie le schema
Kubernetes, mais les definitions amont `JSONSchemaPropsOrArray`,
`JSONSchemaPropsOrBool` et `JSONSchemaPropsOrStringArray` sont sans contrainte.
Trois CRD incorrectes sont donc acceptees par le vrai kubeconform : `items: 42`,
`additionalProperties: 42` et `dependencies: {other: 42}` dans un schema imbrique.
Le risque est un verdict schema vert pour un document dont ces champs ne sont
pas du type attendu. Proposition transmise : restaurer seulement ces trois
unions avec leurs branches schema/tableau/booleen appropriees, en conservant
`JSON` libre pour les valeurs `default`, `example` et `enum` ; ajouter des
controles reels positifs et negatifs. Aucun correctif n'est applique par ce lot.

**Cloture apres le FREEZE final : les trois findings sont corriges.**
Le proprietaire a ajoute `complete_crd_unions` : les trois definitions ne sont
completees que lorsqu'elles sont vides ou limitees a leur description. Une
contrainte deja presente en amont est conservee, ainsi que le type `JSON` libre.
Le test permanent `test_actual_validator_checks_recursive_crd_union_types`
exerce le vrai binaire sur dix cas hors reseau ; notre controle independant
utilise les definitions recursives completes telechargees en amont. Sur la
copie finale, les trois scalaires sont refuses et les sept formes valides
acceptees. Aucun finding bloquant restant dans ce perimetre ; les limites de
catalogue et de validation serveur ci-dessous restent applicables.

`apiregistration.k8s.io/v1` est declare dans les capacites de rendu Helm.
Les CRD sont incluses. Aucun `-ignore-missing-schemas` ou `-skip` n'est utilise ;
une erreur, une ressource invalide, un schema ignore ou un rendu vide echoue.

Les anciens 52 ignores correspondaient a 50 CRD (CNPG 11, Kubescape 11,
KEDA 6, Kyverno 22) et deux APIService `v1beta1` de Prometheus Adapter.
Le nouveau rendu inclut les CRD des charts et passe de 390 a 446 ressources :
**446 valides, zero invalide, zero erreur, zero ignoree**.

La CRD Kubernetes utilise le schema recursif `v1.35.6-local`, compose de
`customresourcedefinition-apiextensions-v1.json` et `_definitions.json`.
La transformation locale ferme les objets types tout en conservant les maps,
les valeurs libres et les nulls optionnels ; elle complete les trois unions
decrites ci-dessus. Le format local conserve les references recursives ; les
formats local et standalone sont produits separement par le
[script amont de generation](https://github.com/yannh/kubernetes-json-schema/blob/master/build.sh).
Aucun convertisseur externe ni nouvelle dependance Python n'est ajoute.

Le garde de compatibilite lit les images rendues, exige des versions stables,
accepte Velero 1.17.x/plugin 1.13.x ou Velero 1.18.x/plugin 1.14.x, et refuse
une nouvelle branche sans revue. Ces paires correspondent a la
[matrice officielle du plugin AWS](https://github.com/velero-io/velero-plugin-for-aws#compatibility).
Le pin deploye est 1.13.2. Le collecteur Hauler le lit depuis les values Velero,
et le test de regression verifie l'absence de pin parallele dans
`scripts/mirror-images.txt` ainsi que la concordance avec le manifeste genere.
Cette verification n'est pas une preuve de sauvegarde/restauration.
